## 5. The seal-only workflow (`hebc-ym-2x5-stage-b-reseal.yml`)

It is generated by `reseal_workflow.py` and has one job. It builds nothing and launches
no cell or merge computation. In order, it:

1. checks the manifest's SHA-256 and its `PASS` total, and runs the generator control;
2. fetches fresh API metadata, which must reproduce the frozen manifest byte for byte;
3. downloads every artifact by ID into `zips/<artifact_id>.zip`;
4. runs `reseal_verify.py` (128 cells, 4 merges);
5. runs the certify script of the fixed generator verbatim, minus the two
   `needs.cell/merge.result` lines, because there are no such jobs.

Before the seal is written, the workflow binds it to everything it used:

- the source run and head;
- this workflow's commit and run ID;
- the manifest's SHA-256;
- the stage A receipt hash;
- the generator file hash and commit;
- the verification and generator-control receipts;
- all 132 artifact IDs.

The downloaded ZIPs are uploaded unchanged, with 90-day retention, for review.

## Verdicts

- **Before the seal.** A failure anywhere before the seal is `INCONCLUSIVE`, never
  `MISMATCH` or a partial seal.
- **In the seal.** The seal step's own gates decide the verdict, as the frozen stage B
  rules require: shard integrity, the shell-gap certificate, monotone cells, and
  `status=PASS`.
