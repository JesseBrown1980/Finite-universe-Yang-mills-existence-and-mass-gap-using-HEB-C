# P2 and P3 in CI: frozen run specification

This file freezes, before any CI run, how the room-backed lane's identity gates P2 and P3
(`MEMORY-PILOT-SPEC.md`) are run on GitHub Actions. The workflow is
`.github/workflows/hebc-ym-room-identity.yml`, generated by
`native/ym/python/room_identity_workflow.py`. Every job runs through the HEB-C HTTP-0
backend (`hebc_ym_http0`). Integer-only, json=0.

The production HOLD in `PRODUCTION-ADMISSION.md` is unchanged. P1 (merge of `ymroom` and
`roomschur` to `main`) is a separate gate and is not decided here.

## Code under test

| item | value |
|---|---|
| `ymroom`, `roomschur` | source unchanged from `c07eef7` (branch `ym-3x4-room-backed`, built and run on Host8/acer) |
| `ymsec`, `shellschur` | unchanged, as on `main` |
| backend routes added | `roomident`, `roombuild`, `roomcount`, `roomcountcols`, `roomcountmerge` (zero-momentum Sx+Sy+ only) |
| `roomschur` settings in the backend | `ROOMSCHUR_K = 8`, `ROOMSCHUR_BUDGET = 12 × 2³⁰` bytes, MAXSWEEP 4000 (as `count`) |
| runtime fields removed from canonical output | `ms=`, `elapsed_ms=`, `pass_ms=` (kept in `run.measure` and in the uploaded evidence) |

## P2: builder identity

For each of 2×3, 2×4 and 3×3: the `sector` job builds the `ymsec` matrix, the `roomident` job
runs `ymroom text` and compares its bytes and SHA-256 with that matrix. Both jobs are
re-executed by `verify`. **PASS** for a lattice: both verify lines PASS and
`ROOM_IDENTITY|…|identical=1`. Anything else, or missing evidence: INCONCLUSIVE.

## P3: runner identity

3×3, Sx+Sy+, JE = 1000, JB = 9000, FDIG = 12 (F = 10¹²), TOL = 1000, MAXSWEEP = 4000.
Core columns are split into frozen chunks `[⌊i·core/S⌋, ⌊(i+1)·core/S⌋)`, the same chunks for
both runners:

| t (milli-units) | core (ddcore, frozen) | chunks S |
|---|---|---|
| 60,000,000 | 101 | 2 |
| 72,000,000 | 1,137 | 16 |
| 90,000,000 | 2,940 | 40 |

Each chunk job builds its own input fresh (`sector` for shellschur, `roombuild` for
roomschur). Each merge job checks that all S chunks returned, rebuilds the input fresh, and
runs `countmerge` / `roomcountmerge`. These merges check shard integrity, the binding of
every chunk to the same input SHA-256 and an exact partition of `0..core`. A merged core
different from the frozen value fails closed.

Comparison: `schur_record_compare.py` on the three (shellschur, roomschur) evidence pairs.
Each evidence file holds every chunk's `run.hbp` plus the merge's `run.hbp`.

- **AGREE:** every summary field and every SCOL record is equal at all three thresholds.
- **MISMATCH:** a fully computed difference.
- **INCONCLUSIVE:** anything missing, failed, timed out, duplicated or truncated.

AGREE on an AMBIGUOUS threshold is implementation agreement, not a spectral PASS.

### Comparator version: decision needed

A pre-run check on 2×3 (local, below) showed that roomschur writes three fields on its
`SHELL_SCHUR_COLS` lines that shellschur does not: `room_bytes_per_pass`, `payload_merkle`
and `pass_ms`. They record where the matrix lives and how long a pass took. The frozen
comparator `v1` (`9f60d56`) compares every field of those lines except `ms=`, so it reports
MISMATCH on them even when every SCOL record and the summary are equal.

`v2` (this branch) excludes those three room-only fields from equality and prints them as
evidence. It also requires every room line to carry one and the same `payload_merkle`;
otherwise the result is INCONCLUSIVE. Every SCOL record and summary field is still compared,
except `matrix=` and `ms=`. Synthetic controls: 21/21
(`schur_record_compare_controls.py`).

The CI receipt prints both verdicts, `v2` and `v1`. **Which one decides P3 is the reviewer's
call.** Until it is made, P3 is reported as both verdicts, not as a pass.

## Addendum: comparator decision (reviewer, 2026-10-29)

**v2 decides P3**, on the condition that its only relaxation relative to v1 is the exclusion
of the three roomschur metadata fields. Every mathematical summary field and every required
record must still be compared. The code difference `9f60d56` → `16ed1a6` was checked against
that condition:

| field | written by | class | what it records |
|---|---|---|---|
| `room_bytes_per_pass` | roomschur only | storage | bytes of the room file streamed per sweep |
| `payload_merkle` | roomschur only | storage | SHA-256 merkle of the room file's payload (16 MiB chunks) |
| `pass_ms` | roomschur only | timing | wall-clock milliseconds per pass (also removed by the backend as runtime, like `ms=`) |

What v2 changes and what it leaves alone:

- **Relaxed:** only the three fields above, and only on `SHELL_SCHUR_COLS` lines. The
  exclusion is by field name, so it would also cover them on the shellschur side. Shellschur
  writes none of them.
- **Unchanged from v1:** the `SHELL_SCHUR` summary comparison (excluding only `matrix=` and
  `ms=`), every SCOL record keyed by `(cb, ca)`, the key sets, the duplicate and missing-key
  rules, and every other `SHELL_SCHUR_COLS` field.
- **Added, both stricter or evidence-only:**
  - all room lines must carry one and the same `payload_merkle`, otherwise the result is
    INCONCLUSIVE;
  - the excluded values are printed in every evidence line.

The receipt keeps both verdicts, neither suppressed. The v1 result is preserved verbatim as the
strict comparator's result. Where v1 reports MISMATCH and v2 reports AGREE, v1's disagreement
is on those metadata fields. It is not a mathematical-record mismatch under the P3 comparison
contract.

**P3 is satisfied for a CI run** only if both hold: v2 reports AGREE at all three thresholds;
the records are valid and complete, and every integrity gate passes.

- AGREE on a shared AMBIGUOUS outcome (expected at t = 90,000,000) is implementation
  agreement, not a spectral PASS.
- This decision changes no completed record, threshold, binary or frozen mathematical input.
- The production HOLD is unchanged until the separate memory pilot and every other admission
  gate pass.

## Addendum: run 40906496344 and the compare-only rerun (frozen before the rerun)

**Run 40906496344 (commit `16ed1a6`).** Every computing job succeeded: the gates, the three P2
jobs, 116 of 116 column jobs and 6 of 6 merges. The compare job did not finish. The runner
received a shutdown signal 85 s into the comparison, and no receipt was produced. Under
fail-closed, P2 and P3 for that run are **INCONCLUSIVE**.

Cause: at t = 90,000,000 each evidence file holds 8,643,600 SCOL records (1.6 GB). The
comparators keep every record as a Python dict, measured at about 1.94 KB per record, so
about 17 GB per side against a 16 GB runner.

**Rerun.** `hebc-ym-room-identity-recompare.yml` compares the evidence again. It recomputes
nothing.

1. **Admission.** The 9 evidence artifacts (p2-0..2 and p3m-{shell,room}-{60,72,90}M) are
   downloaded by frozen artifact ID. Each zip's SHA-256 must equal the digest GitHub recorded
   at upload. It is all or nothing; any failure gives INCONCLUSIVE. Each evidence file's own
   `.sha256` sidecar is then checked.
2. **Comparator implementation.** `schur_record_compare_stream.py` applies the same rules as v2,
   or as frozen v1 with `--v1`, using about 1/8 of the memory: the shell side is held as one
   canonical string per record, and the room side is streamed against it.
3. **Equivalence, required before any verdict counts.**
   - all synthetic control cases, each also with sides swapped, against both v2 and frozen v1;
   - the real t = 60M and 72M pairs, where the originals fit in memory, run four ways (v2, v2
     stream, v1, v1 stream);
   - the stream output must be byte-identical to the original's in every case.
4. **Decision.** The stream implementation of v2 decides P3, under the reviewer decision above.
   The stream implementation of v1 is reported in full as the strict result.
5. **P2.** Checked as before: two verify lines and `identical=1` per lattice.

Any admission, integrity or equivalence failure makes P3 INCONCLUSIVE whatever the comparison
says.

**Rerun attempt 1: run 40925767993 (commit `2ec18ca`). INCONCLUSIVE, workflow defect.** These
steps completed:

- admission, 9 of 9 artifacts by ID and zip SHA-256;
- the evidence sidecars;
- P2 for all three lattices;

The step then stopped at the first comparator that exits nonzero by design (v1 at t = 60M,

**Fix.** An explicit `set +e` at the top of the step. The same latent defect is fixed in
`room_identity_workflow.py`, which generates the compare step of the main workflow. The
generated YAML is not regenerated here, because that would start another 116-job run; it is
regenerated before its next run.

No record, threshold, comparator rule or frozen input changed.
